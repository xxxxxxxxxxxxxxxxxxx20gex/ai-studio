## Q1: 详细说明RLHF的完整流程

**建议结构：流程图 + 每一步目标 + 4 个模型。**

```text
Step 0: 预训练基础模型
  - 用海量无监督语料训练 GPT 类模型

Step 1: SFT（监督微调）
  - 数据：高质量 指令-回答 对
  - 目标：让模型学会“听人话、按指令回答”

Step 2: 训练 Reward Model（奖励模型）
  - 数据：同一个 prompt 下，多条回答的人类偏好排序
  - 目标：学会给回答打分，估计人类喜好

Step 3: 用 PPO 做强化学习优化
  - 用 SFT 模型作为初始策略
  - 用 Reward Model 给回答打分
  - 用 KL 散度约束策略不要偏离参考模型太多
  - 持续迭代，得到最终对齐模型（类似 ChatGPT）
```

**4 个模型的角色：**

- **Actor（策略模型）**：当前在优化的主模型，用来生成回答；
- **Critic（价值模型）**：估计状态价值，用来计算优势函数，稳定训练；
- **Reference（参考模型）**：SFT 模型的冻结副本，用于 KL 约束；
- **Reward Model（奖励模型）**：根据人类偏好打分，提供奖励信号。

可以配一段总结性口述：

> 「一句话总结 RLHF：先用 SFT 把模型训练到『会听话』，再用人类偏好训练出一个奖励模型，最后用 PPO 在奖励模型的指导下继续优化，同时用 KL 散度约束策略不要跑偏。」

## Q2: 解释PPO的核心约束——KL散度的作用

**问题背景：**

如果只最大化奖励：

```text
Loss = -E[ reward(x, y) ]

问题：
- 模型会想办法“作弊”奖励模型（reward hacking）
- 可能生成重复、奇怪但得分很高的回答
- 甚至会导致模式崩溃（mode collapse）
```

**PPO 目标函数：**

```text
maximize: E[ r(x, y) ] - β · KL(π_θ || π_ref)

其中：
- r(x, y)：Reward Model 给的分数
- π_θ：当前策略（Actor）
- π_ref：参考策略（Reference，通常是 SFT 模型）
- β：KL 惩罚系数（控制约束强度）
```

**KL 散度公式：**

```text
KL(π_θ || π_ref) = E_y[ log π_θ(y|x) - log π_ref(y|x) ]
```

**直观解释：**

> 「KL 散度度量的是『当前策略』和『参考策略』的差异。  
> 如果 Actor 为了拿高分疯狂偏离 SFT 的分布，KL 会变大，被惩罚；  
> 所以最终的行为是在『提高奖励』和『保持不太偏离原来模型』之间做平衡。」

**例子：**

```text
无 KL 约束：
  Prompt: "介绍一下北京"
  早期输出：正常段落
  若 Reward Model 偏好某种模式，模型可能学会："北京北京北京..." 这类重复，骗高分

有 KL 约束：
  一旦输出分布和 SFT 模型差太多，KL 项很大，整体目标反而变差，
  模型就会被拉回到更“正常”的分布附近。
```

## Q3: DPO为什么更简单？核心创新是什么？

**第一层回答（直觉版）：**

> 「DPO 的核心想法是：**绕过 Reward Model，直接从人类偏好数据优化策略**。  
> 不再显式训练奖励模型，也不需要 Critic，只保留『Policy + Reference』两个模型，所以显存占用和工程复杂度都比 PPO 小得多。」

**对比 PPO 流程：**

```text
PPO:
  1. 预训练基础模型
  2. SFT 监督微调
  3. 训练 Reward Model（排序数据 → 打分器）
  4. 用 PPO 做 RL 优化（Actor + Critic + Ref + RM）

DPO:
  1. 预训练基础模型
  2. SFT 监督微调
  3. 直接在偏好对 (y_w, y_l) 上优化策略（Policy + Ref）
```

**DPO 损失函数（只需要记住形式和含义）：**

```text
L_DPO = -E[ log σ( β·log(π_θ(y_w|x)/π_ref(y_w|x))
                   - β·log(π_θ(y_l|x)/π_ref(y_l|x)) ) ]

其中：
- y_w: 更好的回答 (winner)
- y_l: 较差的回答 (loser)
- π_θ: 当前策略
- π_ref: 参考策略（SFT 模型）
- β: 温度/强度系数
```

**直观理解：**

> 「DPO 直接让模型去提高『相对于参考模型』产生好回答的概率，降低坏回答的概率，相当于把『偏好排序 → 奖励模型 → RL』这一长链子数学上压缩成一个可直接优化的损失函数。」

**为什么更简单：**

1. 不需要单独训练 Reward Model；
2. 不需要 Critic，不是真正意义上的 RL；
3. 显存占用减半（2 个模型 vs 4 个模型）；
4. 实现起来更像「带特殊损失函数的监督学习」。

## Q4: 何时选择PPO vs DPO？

**推荐回答结构：**

1. 先给一张简洁对比表；
2. 再给几个典型场景。

**对比表：**

```text
| 维度         | PPO                        | DPO                         |
|--------------|---------------------------|-----------------------------|
| 模型数量     | 4 个 (Actor, Critic, Ref, RM) | 2 个 (Policy, Ref)       |
| 工程复杂度   | 高                         | 低                          |
| 显存/算力需求| 大                         | 小                          |
| 训练稳定性   | 依赖 RM 质量、较复杂       | 相对更稳定                  |
| 数据形式     | 奖励分数或排序 + 轨迹       | 偏好对 (better vs worse)   |
| 适用场景     | 大厂、大规模、复杂约束     | 开源、学术、中小规模       |
```

**选择 PPO 的典型场景：**

```text
1. 资源非常充足（多机多卡、专用集群）
2. 有比较明确、可编程的奖励函数：
   - 例如：通过单元测试、符合安全规则等
3. 需要在线交互、持续收集反馈
4. 对性能和可控性要求极高（如顶级商用产品）
```

**选择 DPO 的典型场景：**

```text
1. 资源有限（1～几张 GPU）
2. 只有偏好标注数据（成对比较）
3. 希望快速搭建对齐流程、减少工程负担
4. 以开源模型/研究项目为主，追求简单稳定
```

**加分总结：**

> 「目前工业界大厂内部依然大量使用 PPO，因为它和传统 RL 框架兼容、可控性强；  
> 而在开源社区和中小团队中，DPO 因为只需要两个模型、实现简单、显存压力小，已经成为对齐开源大模型的主流选择。」
